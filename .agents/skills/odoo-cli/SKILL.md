# Odoo CLI 项目管理

使用当前项目的真实命令和配置完成任务，不创建新的项目管理协议。

## 先定位项目与入口

- 在目标项目确认 `compose.yaml`、`.env.example`；从子目录运行会向上寻找项目。CLI 源码库或纯模块库未必是可运行项目。
- 操作其他目录时用全局参数：`odoo --project /path/to/project <命令>`，`--project` 放在子命令前。先读目标项目的 AGENTS.md。
- 用 `odoo --version` 和相应 `--help` 核对能力。未知或报错的参数先查帮助，不猜测新命令。
- `.env` 已存在就保留。首次初始化可用 `odoo init`；CLI 0.1.0 会覆盖模板的显式密码，遇到该版本时用项目现有的 `node scripts/dev.mjs init`，或使用支持此规则的 0.1.1+。
- 缺少全局 CLI 时，先看项目内 `node scripts/dev.mjs --help`；仅使用它实际支持的语法。模块/数据库列表等能力需要管理 CLI。需要安装时使用 `npm install -g @mjh-odoo/cli`。

## 操作约束与交付

- 查看配置用 `odoo config`，输出已脱敏。需要判断本机密码是否配置时只在本机读取必要字段，不把整份 `.env` 或真实密码写进日志、提交、PR 或任务记录。
- 只读排查先用 `status`、`config` 和有限日志；不要为读取日志自动启动服务或重建镜像。缺少 `.env` 时说明尚未初始化，按任务需要处理。项目内兼容脚本的读取副作用可能不同，调用前检查已有配置与帮助。
- `down` 保留数据卷；仅当用户已明确要求删除该项目数据时使用 `-v/--volumes`。已有目标库的覆盖只在用户明确要求时带 `--force`；沿用已有授权，不重复索要确认。
- 安装/升级和恢复会停止该项目的 Odoo。失败时保留停止状态与维护输出，修复后再启动，不把普通服务日志当成一次性维护容器的完整记录。
- 数据库存档是 Odoo 原生 ZIP，代码和模块由项目 Git 独立维护；回退代码不会撤销数据库升级。
- 一次操作完成后报告目标项目/数据库、实际结果及未验证内容。查询为空只代表查询范围没有结果；执行成功不等于业务验收通过。
